## 5. Persisted Artifact Model

Every artifact family shares one model (`persistence/envelope.py`):
an **immutable version file** (`v<N>.json`, containing `artifact_id`,
`artifact_version`, `generated_at`, `generator`, `provenance`,
`content_hash`, and the full `payload`) plus one **mutable pointer
file** (`latest.json`, containing `latest_version`, `latest_path`, and
an append-only `history` list). A version file, once written, is never
edited or deleted by this code. Two payloads that differ only in their
`generated_at` timestamp are treated as the same fact re-observed
(`reused: true`, no new version) — a genuinely different regeneration
gets its own new, permanently retained version. This satisfies §16
("do not overwrite a previously governed artifact without provenance"
/ "avoid duplicate artifact collisions") without inventing a bespoke
scheme per checkpoint.

## 8. RBTP — Risk-Based Test Prioritization (§2/§6)

Every risk factor is either:
* **evidence-derived** — `business_criticality` from the testcase's own
  already-governed `priority` field; `security_impact` from a
  deterministic keyword scan over the real, approved requirement text
  (`password`, `credential`, `authenticat`, `login`, `cvv`, `credit card`,
  `payment` — narrowed during this task's own testing after `account`
  and bare `card` produced real false positives, e.g. REQ-WISH-03's
  "...without requiring an account"); `customer_impact` from real,
  approved journey membership via a fixed, disclosed
  journey→impact-tier table (J-01/J-02 → HIGH, J-03/J-04 → MEDIUM,
  J-05 → LOW); or
* **explicitly `UNKNOWN`** — `risk_likelihood`, `change_impact`,
  `defect_history` (no defect-tracking/change-history/likelihood data
  source exists anywhere in this project — verified by inspection, not
  assumed) and `dependency_impact` (the Dependency Matrix runs *after*
  RBTP in this pipeline, per the target architecture, so it cannot yet
  be evidenced when RBTP is generated).

`priority` (P0–P3) and `execution_recommendation` are derived
deterministically from only the three known factors; a fixed rationale
string names every factor, its value, and its evidence (or the reason
it is UNKNOWN) — **the "why is TC-X P0 while TC-Y P2" requirement is
answerable directly from the persisted `risk_rationale` string alone**,
verified by `tests/test_cr001_rbtp.py::test_priority_is_explainable_from_the_persisted_rationale_alone`.

An optional LLM (`llm/rbtp_client.py`) may append only a short,
non-authoritative narrative elaboration; `tests/test_cr001_rbtp.py::test_llm_narrative_is_appended_but_never_authoritative`
proves the deterministic factors/priority are byte-identical whether or
not the LLM is used. Live end-to-end run (StubRBTPClient) produced 9
real RBTP records, e.g. `RBTP-TC-REQ-REG-01-02`: `priority=P0`,
`business_criticality=HIGH`, `security_impact=HIGH` (matched `password`),
`customer_impact=HIGH` (journey J-01).

**Live-Claude verification attempted, BLOCKED (disclosed, not
fabricated):** `ClaudeRBTPClient()` was invoked against the real
accepted `REQ-REG-01` testcase; the Windows-side Python subprocess
environment used for this batch's automation could not resolve the

`None`) — a cross-environment `PATH` resolution limitation of this
specific verification attempt, not a defect in `ClaudeRBTPClient`
itself, which correctly raised `ClaudeProviderError` rather than
silently falling back or fabricating a narrative. The RBTP
narrative-elaboration surface remains fully covered by 10 deterministic

**Distinctness from the Dependency Matrix**, verified by
`tests/test_cr001_rbtp.py::test_rbtp_and_dependency_matrix_schemas_are_disjoint`:

## 9. Dependency / Reusability Matrix (§7)

Fully deterministic, zero LLM involvement. `dependencies/generate.py`
computes pairwise edges (`SHARED_JOURNEY`, `SHARED_PRECONDITION`,
`SHARED_REQUIREMENT`) via plain set/equality overlap over already-governed
CP-03 testcase fields, plus surfaces CP-03's own `POSSIBLE_DUPLICATE_OF`
reasons as `POSSIBLE_DUPLICATE_TESTING` edges — no new duplicate-detection
rule is invented. A `reusable_component_candidate` requires **literal,
exact** precondition-text repetition across 2+ distinct testcases; a
single testcase's precondition never produces a candidate (unit-tested).
Live run over the 4 profiled requirements' real, governed testcases: 30
edges, 4 reusable-setup candidates, schema validation `passed: true`.

## 12. Discovered Advisory — `AUTOMATION_ID_COLLISION_ADVISORY` (new finding, not a defect in this batch)

Persisting real CP-05 output surfaced a pre-existing characteristic of
the **frozen** `automation/generate.py` (`automation_id=f"PW-{testcase_id}-01"`,
line ~183): the ID does not incorporate the paired dataset's ID, and its
numeric suffix is always `-01` regardless of how many eligible datasets
a testcase has. `TC-REQ-REG-01-01` had 6 eligible CP-04 datasets, so CP-05
generated 6 **genuinely different** `PlaywrightArtifact`s (different
`test_data_set_id` each) that all collide on the single automation_id
`PW-TC-REQ-REG-01-01-01`.

This was invisible before any persistence existed. This batch's
`persistence.envelope` handled it **safely** — no data was lost; all 6
distinct artifacts were retained as immutable versions 1–6 under that
one artifact_id — but semantically, `automation/generated/PW-TC-REQ-REG-01-01-01/latest.json`
does not point to "the current version of one logical automation"; it
points to "whichever of 6 distinct automations was persisted most
recently." **This is not fixed by this batch** (fixing it means editing
`automation/generate.py`'s frozen `automation_id` construction, which
this task's governing rules prohibit without a separate Change Request).
It is reported here as a discovered, disclosed gap requiring a future
Change Request against frozen CP-MVP2-05 (e.g., incorporating
`test_data_set_id` into `automation_id`) — not worked around silently,
not hidden.

## 13. Execution Persistence + Summary (§13/§14)

`execution/persist.py` and `execution/summary.py` are purely additive;
`execution/{schema,validate,evidence,engine,pipeline}.py` are byte-for-byte
unchanged (`git diff` empty, re-verified after this task).

**Design decision on the directory-convention question (§13's own
fallback instruction):** the frozen CP-MVP2-06 final-implementation-freeze
checkpoint already cites real evidence paths under
`runs/cp_mvp2_06/<execution_id>/...`. Changing that *default* would
retroactively invalidate paths a **closed** checkpoint already cites as
evidence — an unacceptable silent break of an existing consumer. The
safest backward-compatible approach was implemented instead:
`execution/persist.py::persist_execution_result` is a **separate,
additive** function any caller may invoke, by composition, alongside
the unmodified `run_cp_mvp2_06()`, writing the requested
`runs/YYYY/MM/DD/<execution_id>/{final_result,step_results,assertions}.json`
layout as an **additional, parallel** record of the same real
`ExecutionResult` — never a replacement for, and never mutating,
CP-06's own frozen evidence. Verified: `test_persist_execution_result_never_touches_frozen_evidence_module`
asserts `execution.evidence.RUNS_DIR` is never reassigned.

`execution/summary.py::build_execution_summary` explicitly distinguishes
(per §14's own instruction) **execution coverage** (planned vs. actually
executed, i.e. non-`NOT_EXECUTED`), **testcase coverage** (distinct
`testcase_id`s present, regardless of outcome), and **requirement
coverage** (a requirement counts *only* via a `PASS` execution — never
merely because a testcase/automation exists for it).

Live run: 22 real `ExecutionResult`s (all `NOT_EXECUTED`, consistent with
§11's finding — no eligible CP-05 artifact exists), each persisted under
a real `runs/2026/09/14/<execution_id>/` directory with real 2026-09-14
timestamps; summary persisted showing `counts_by_status: {PASS: 0, FAIL: 0,
BLOCKED: 0, NOT_EXECUTED: 22, ERROR: 0}` and
`requirements_with_a_passing_execution: []` — honestly reflecting that
zero requirements are covered by a passing execution, never inflated by
existence alone.

## 19. Limitations / Known Advisories

1. **`AUTOMATION_ID_COLLISION_ADVISORY`** (§12, new this task) — CP-05's
   `automation_id` generation does not incorporate the paired dataset ID;
   a testcase with multiple eligible datasets produces multiple distinct
   automations sharing one ID. Persistence handled this safely (no data
   loss) but the "latest version" semantics are misleading for such
   cases. Requires a future Change Request against frozen CP-05.
2. No `ACCEPTED`/`POSSIBLE_DUPLICATE` CP-05 automation artifact currently
   exists (carried forward, unchanged, from CP-05/CP-06).
3. RBTP's `dependency_impact` factor is structurally `UNKNOWN` at
   generation time in this pipeline ordering (Dependency Matrix runs
   after RBTP) — disclosed, not a defect.
4. `risk_likelihood`, `change_impact`, `defect_history` are `UNKNOWN`
   for every testcase in this project — no data source exists anywhere
   to evidence them.
5. Live-Claude verification of `llm/rbtp_client.py::ClaudeRBTPClient`
   was attempted and BLOCKED by a cross-environment `PATH` resolution
   issue (§8) — not a code defect, disclosed rather than worked around.
6. Reusable Playwright *code* components (page objects, helper modules)
   are not scaffolded by this batch — only real, evidence-backed
   *candidates* are identified (§11); actually extracting a component
   is left for a future task once a real `ACCEPTED` automation artifact
   exists to refactor.
7. `execution/summary.py`'s persisted summaries and `execution/persist.py`'s
   timestamped logs exist as a parallel record alongside, not a
   replacement for, CP-06's own frozen `runs/cp_mvp2_06/` evidence.
