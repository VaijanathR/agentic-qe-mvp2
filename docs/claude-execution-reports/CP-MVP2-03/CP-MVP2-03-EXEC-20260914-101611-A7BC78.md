## E. LLM Generation

* **Input:** the governed `requirement_context` dict (`requirement_id`, `requirement_text`, `source_document`, `source_version`, `approval_status`, `journey_id`, `evidence[]`) built exclusively from `KnowledgeBase.by_id()` results.
* **Retrieval context:** for a requirement's POSITIVE justification, the requirement chunk itself; for ALTERNATE, any approved `business_rule` chunk directly linked to the requirement ID; for EXCEPTIONAL, any approved `negative_case` chunk belonging to the requirement's own journey (via the journey_index membership list). All three are real, already-ingested CP-MVP2-02 data — nothing was invented to obtain them.
* **Generation mechanism:** `LLMClient.propose_testcases(requirement_context, scenario_types)`. Two implementations:
  * `OpenAILLMClient` — real backend, calls the OpenAI chat-completions API with a system prompt that restricts the model to the supplied evidence and instructs strict JSON output; parses and validates the response is a JSON list.
  * `StubLLMClient` — deterministic offline stand-in (see report section K, "Limitations").
* **Output structure:** raw candidates carry only `scenario_type, title, preconditions, test_steps, expected_result, priority` — deterministic code in `testcases/generate.py` then assembles the full `Testcase` record (`testcase_id`, `requirement_ids`, `journey_id`, `source_attribution`, `generation_metadata`), never trusting the model for those fields.

## F. Governance

* **Traceability validation:** `validate_traceability` resolves each `requirement_id` to its canonical (highest-authority) `requirement` chunk; missing/empty IDs and unknown IDs are distinguished from "known but not approved" (draft leakage). Verified by `test_valid_requirement_mapping_is_accepted`, `test_missing_requirement_id_is_rejected`, `test_unknown_requirement_id_is_quarantined`, `test_orphan_testcase_is_not_accepted`.
* **Draft protection:** `govern_testcase` returns `REJECTED` (never `ACCEPTED`) whenever any mapped requirement ID resolves only to non-approved/draft content. Verified by `test_draft_leakage_cannot_produce_an_accepted_testcase` against a synthetic single-chunk KB (the real corpus has no requirement that exists *only* in draft — every draft requirement in this corpus has an approved counterpart — so a true draft-only leak cannot be demonstrated against real data; this is disclosed, not hidden, and mirrors the same synthetic-mechanism-test convention already used in `tests/test_cp_mvp2_02_knowledge.py::check_version_supersession`).
* **Unsupported requirements:** `generate_for_requirement` returns an explicit `unsupported` dict (reason + detail, no fabricated testcase) when a requirement doesn't resolve to approved evidence, or resolves but no requested scenario is justified. Verified by `test_unsupported_requirement_is_reported_with_reason` (real ID `WISH-OQ-01`, an approved-SRS open_question, not a requirement) and `test_scenario_not_manufactured_without_justifying_evidence` (real ID `REQ-WISH-02`, no business-rule/negative-case evidence).
* **Duplicate detection:** `check_duplicate_testcase_ids` (exact ID collisions) and `detect_duplicates` (content-level: exact repeat -> `DUPLICATE`; same requirement+scenario, different wording -> `POSSIBLE_DUPLICATE`, kept not dropped). Verified by `test_duplicate_testcase_ids_are_detected`, `test_obvious_duplicate_testcase_is_classified_duplicate`, `test_distinct_wording_same_requirement_and_scenario_is_possible_duplicate_not_dropped`.
* **Coverage calculation:** `calculate_coverage` counts only `ACCEPTED`/`POSSIBLE_DUPLICATE` testcases whose requirement IDs are members of the applicable set. Verified by `test_coverage_is_calculated_deterministically`, `test_uncovered_requirements_are_reported`, and `test_invalid_or_untraceable_ids_never_inflate_coverage` (a force-constructed out-of-universe `ACCEPTED` record is still excluded by the coverage function's own defensive filter).
* **Attribution:** every generated `Testcase.source_attribution` entry is built from the actual retrieved chunk (`requirement_id`, `source_document`, `source_version`, `chunk_id`) — verified by `test_accepted_testcase_preserves_source_attribution` against real data (`requirements/MVP2_SRS_v1.0_APPROVED.md`, version `1.0`).

## K. Limitations

1. **No live LLM call was exercised.** This sandboxed execution environment has no `OPENAI_API_KEY` configured. `OpenAILLMClient` was verified only for its fail-fast behavior (`test_openai_backend_fails_fast_without_credentials`) — a real generation call, and the JSON-parsing path for actual model output, has **not** been run. All functional/governance/coverage/duplicate/traceability tests exercise `StubLLMClient`, a disclosed, deterministic, offline stand-in for the reasoning step (documented in `llm/client.py` and `docs/CP-MVP2-03-IMPLEMENTATION.md`). This is not a fabricated success: it genuinely proves the retrieval -> reasoning-boundary -> governance wiring is correct and that governance holds for *any* conforming `LLMClient`, but it does **not** prove a live OpenAI response would parse cleanly end-to-end. Enabling and re-verifying the real backend requires a human/Di decision to provision `OPENAI_API_KEY` in an environment with network access.
2. `test_data_reference` is always `None` — CP-MVP2-04 does not exist yet.
3. Duplicate detection has no semantic-similarity model, only exact-normalization plus a same-requirement/scenario heuristic (spec allows this — "semantic similarity where practical" — and an embedding dependency was judged not practical to add for this checkpoint).
4. ALTERNATE/EXCEPTIONAL scenario justification is currently limited to two specific, deterministic evidence-linkage mechanisms (direct business-rule citation; same-journey negative-case membership). A requirement whose alternate/exceptional evidence exists in the Approved SRS in some other form will correctly produce only a POSITIVE scenario rather than an invented one — by design, but it bounds how much ALTERNATE/EXCEPTIONAL coverage this implementation can currently surface.
5. The draft-leakage-rejection test uses a synthetic single-chunk KB rather than real data, because no real requirement in this corpus exists in draft only (every draft requirement has an approved counterpart) — disclosed above and in the test's own docstring, consistent with the existing CP-MVP2-02 test suite's own synthetic-mechanism-test precedent.
