### Provider architecture implemented

```text
testcases/  ->  LLMClient  ->  ClaudeLLMClient  ->  claude CLI (subprocess)  ->  authenticated Claude Pro session
```

Matches `docs/CP-MVP2-03-CLAUDE-PROVIDER-DECISION.md` sec. 4/6/14 exactly: the adapter sits behind the existing `LLMClient` abstraction; nothing else in `testcases/` was changed to accommodate it, so the rest of the pipeline remains provider-agnostic.

### Subprocess behavior

* Invocation argv: `[claude, -p, <json-encoded user prompt>, --append-system-prompt, <system prompt>, --output-format, json, --restricted, (--model <model> if configured)]`.
* `subprocess.run(argv, capture_output=True, text=True, timeout=..., shell=False)` — an **argument list**, `shell=False` explicitly passed; no string concatenation or shell interpolation anywhere in the call path. Verified by `test_argv_is_a_list_not_shell_and_uses_restricted_mode` and `test_requirement_text_with_shell_metacharacters_is_passed_as_a_single_safe_argument` (a requirement text containing `; rm -rf / #$(whoami)\`id\`` plus a newline, quotes, and a Unicode character is confirmed to arrive intact, as one JSON-encoded argv element, never split or reinterpreted).
* `--restricted`: Claude Code's own documented flag removing built-in Bash/PowerShell/REPL/WebFetch tool access, so the call cannot read or write repository files — enforced by construction of the argv, verified present in every invocation by the same argv test.
* Timeout: explicit, configurable (`CP_MVP2_03_CLAUDE_TIMEOUT_SECONDS`, default 120s), always passed to `subprocess.run`; `subprocess.TimeoutExpired` is caught and converted to `ClaudeProviderError` (verified by `test_timeout_raises_provider_error`, `test_explicit_timeout_is_always_passed_to_subprocess_run`).
* stdout/stderr captured separately; stderr is never merged into a successful result, and is included (truncated to 2000 chars) only in a failure's error message (verified by `test_stderr_present_alongside_success_is_ignored_not_merged`, `test_non_zero_exit_code_raises_provider_error`).
* Non-zero exit code always raises, even when stdout happens to contain something that would otherwise parse as a valid response (`test_non_zero_exit_is_never_interpreted_as_success`).

### Parsing

Parses the `--output-format json` envelope (`is_error`, `result`), then parses `result` itself as the JSON array of narrative candidates. Every failure mode raises `ClaudeProviderError` rather than falling back to text parsing or a fabricated result: empty stdout, invalid envelope JSON, non-object envelope, `is_error: true`, missing/non-string/empty `result`, non-JSON `result` text, non-list parsed `result`. Each has a dedicated test (see Testing, below).

### Error handling / exit-code handling

Distinguishes, all via `ClaudeProviderError` with a specific message prefix so callers/logs can classify the failure: executable not found, billing-safety guard tripped, process start failure (`OSError`), timeout, non-zero exit, empty stdout, malformed envelope, `is_error`, missing/invalid `result`.

### Security controls

* **Credential handling:** `ClaudeLLMClient` never reads, requires, prints, logs, or persists `ANTHROPIC_API_KEY`. If it is merely *present* in the environment, construction raises `ClaudeProviderError` before even checking the CLI's existence (verified by `test_anthropic_api_key_present_raises_provider_error_before_touching_cli`, which asserts `shutil.which` was never called). The guard's error message never includes the variable's value (verified by `test_anthropic_api_key_value_never_appears_in_error_message`, using a fake secret string and asserting it does not appear in the raised exception's text).
* **Injection safety:** covered above (Subprocess behavior).
* **No credential leakage into argv:** `test_credentials_are_never_included_in_argv` asserts neither the literal string `ANTHROPIC_API_KEY` nor any `sk-`-prefixed value appears anywhere in the constructed argv.
