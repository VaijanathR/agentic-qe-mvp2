## Design Decision — `llm/client.py` Not Modified

`docs/CP-MVP2-03-FINAL-FREEZE-CHECKPOINT.md` explicitly lists the Claude provider adapter in `llm/client.py` as frozen scope. Its only abstract method, `LLMClient.propose_testcases()`, hard-codes a testcase-shaped prompt/response contract inapplicable to field-value reasoning. Rather than modify the frozen file (forbidden) or repurpose a wrong-shaped call (would misrepresent the interaction), a **new, parallel** file `llm/test_data_client.py` was added, reusing `ClaudeProviderError` (imported, not redefined) and the identical Claude Pro subscription/subprocess-safety mechanism (`claude -p --restricted`, argument-list `subprocess.run` with `shell=False`, explicit timeout, `ANTHROPIC_API_KEY` billing-safety guard). `git diff` against `llm/client.py`, taken both before and after this entire implementation, is empty.

  1. `StubTestDataClient`'s original `_positive_fields()` helper generated `password`/`confirm_password` independently, producing an accidental mismatch. Fixed to make dependent fields copy their referenced field's already-generated value.
  2. `testdata.generate._field_spec_dict` omitted `dependency_reference` from the context shown to the LLM/stub, which the fix above depends on. Added.

Fixed by recognizing "a field the profile normally marks `MUST_BE_UNIQUE` but this dataset explicitly carries as `MAY_REUSE`" as itself a governed signal of intentional documented invalidity — the actual collision is confirmed later, at batch level, by `enforce_uniqueness`.

## Live Claude Verification

Performed as a single, controlled execution of the actual, unmodified `testdata.pipeline.run_cp_mvp2_04()` with the real `ClaudeTestDataClient`, anchored on a real `ACCEPTED` CP-MVP2-03 testcase for `REQ-REG-01` (that anchor testcase was itself produced via CP-MVP2-03's own real, unmodified pipeline using `StubLLMClient` — a deterministic, non-live call, used only to supply a genuine governed CP-MVP2-03 evidence object, not the subject of this verification).

* Authentication: `claude auth status` → `loggedIn: true`, `authMethod: "claude.ai"`, `apiProvider: "firstParty"`, `subscriptionType: "pro"`. `ANTHROPIC_API_KEY`: confirmed **NOT SET** in the current shell and a fresh login shell.
* Invocation: **SUCCESS.** Elapsed **20.21 seconds** — a genuine subprocess round trip.
* Response parsing: **SUCCESS** — the outer `--output-format json` envelope and inner `result` field both parsed cleanly as JSON, no markdown fence, no explanatory prose (consistent with the CP-MVP2-03 5-call characterization study's dominant observed format).
* Structured data produced: 5 candidate datasets (1 `POSITIVE`, 4 `EXCEPTIONAL`), each with genuinely reasoned, contextually appropriate field values — e.g. the malformed-email case used the literal `"not-an-email"` documented example verbatim; the duplicate-email case reused the *same* email as the `POSITIVE` dataset (`priya.sharma@example.com`) under a *different* name (`Rahul Verma`), correctly modeling "this email is already registered by someone else."
* Deterministic validators processed it: **all 5 datasets reached a governed status** — 2 `ACCEPTED` (`POSITIVE`, and the first `EXCEPTIONAL` "all fields blank" case), 3 `POSSIBLE_DUPLICATE` (the other three `EXCEPTIONAL` cases — same `(testcase_id, EXCEPTIONAL)` mapping key, differing content — correctly flagged, not dropped). **Zero `REJECTED`, zero `QUARANTINED`.**
* Attribution: deterministic, identical across all 5 datasets — `{"requirement_id": "REQ-REG-01", "source_document": "requirements/MVP2_SRS_v1.0_APPROVED.md", "source_version": "1.0", "chunk_id": "srs_v1.0__REQ-REG-01"}` — never trusted from the model.
* Governance: the LLM's own `validity`/`data_category` self-labels were independently confirmed by `validate_constraints` for every dataset (each `INVALID`-labeled dataset actually violated something recognized: blank mandatory fields, a password/confirm-password mismatch, a malformed email format, or the documented uniqueness-override signal for the duplicate-email case) — none were accepted on the LLM's say-so alone.
* Coverage: **1/1 applicable testcase covered, 100%** — computed by the real, unmodified `calculate_coverage`, not asserted independently.
* Uniqueness: the `email` field on the `POSITIVE` dataset carried `MUST_BE_UNIQUE`; the duplicate-email dataset's `email` field correctly carried the documented `MAY_REUSE` override, so `enforce_uniqueness` did not (and should not) flag a collision between them — this is the intended behavior for a deliberately-reused value, not a bug.

**No implementation code was modified as a result of this verification — none was needed. The response format observed here matched the adapter's expectations without requiring a fence-stripping fallback or any other parsing tolerance.**
