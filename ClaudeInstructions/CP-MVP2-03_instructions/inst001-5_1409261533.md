> **Generate governed, traceable testcases from requirements retrieved through the frozen MVP2 Knowledge Base/RAG layer.**

The implementation must demonstrate this governed flow:

```text
APPROVED SRS
      ↓
MVP2 KNOWLEDGE BASE
      ↓
GOVERNED RAG RETRIEVAL
      ↓
RETRIEVED REQUIREMENT CONTEXT
      ↓
LLM
      ↓
STRUCTURED TESTCASE OUTPUT
      ↓
DETERMINISTIC VALIDATORS
      ↓
COVERAGE / TRACEABILITY / GOVERNANCE
      ↓
CP-MVP2-03 RESULT
```

The architectural principle is:

> **RAG supplies the evidence.
> LLM performs the reasoning.
> Deterministic code decides whether the output complies.**

# 6. LLM TESTCASE GENERATION

* understand the requirement
* reason about applicable scenarios
* generate testcase steps
* generate expected outcomes
* assist testcase-to-requirement mapping

* become the final governance authority
* determine coverage without deterministic validation
* silently override deterministic validation

# 9. TRACEABILITY

Every accepted testcase MUST have valid requirement traceability.

The implementation must validate:

```text
TC
 ↓
Requirement ID
 ↓
Approved SRS
 ↓
Source document/version
 ↓
Retrieved evidence
```

Required governance behavior:

### Valid requirement ID

→ testcase may proceed to acceptance.

### Missing/empty requirement ID

→ reject or quarantine testcase.

### Unknown requirement ID

→ reject or quarantine testcase.

### Orphan testcase

→ must not be accepted.

A testcase that cannot be traced to an approved requirement does not count as valid coverage.

---

# 10. COVERAGE CALCULATION

Implement deterministic requirement coverage.

Use:

```text
Requirement Coverage =
Requirements having ≥1 valid testcase
/
Total applicable requirements
× 100
```

The implementation must report at minimum:

* total applicable requirements
* covered requirements
* uncovered requirements
* coverage percentage

Important:

> Fake, invalid, unknown, or untraceable requirement IDs MUST NOT contribute to coverage.

Coverage must be calculated by deterministic code, not trusted from the LLM.

---

# 11. APPROVED VS DRAFT GOVERNANCE

This is a mandatory governance test.

### Approved requirements

Approved requirements are eligible for testcase generation.

### Draft requirements

Draft requirements are NOT eligible to become accepted testcases.

If Draft content leaks into retrieved context:

1. Detect it.
2. Prevent it from becoming an accepted testcase.
3. Record the governance result.

The implementation must explicitly demonstrate that **Draft leakage cannot produce an accepted testcase**.

Do not simply rely on the LLM prompt to prevent this.

Deterministic governance must enforce the rule.

---

# 12. DUPLICATE DETECTION

Implement deterministic duplicate detection appropriate to CP-MVP2-03.

At minimum identify:

* duplicate testcase IDs
* obvious equivalent testcase definitions

Where practical, support semantic similarity or equivalent duplicate reasoning.

Use the defined statuses:

```text
UNIQUE
DUPLICATE
POSSIBLE_DUPLICATE
```

Important:

Do NOT aggressively delete potentially distinct testcases merely because they have similar wording.

In particular, testcases with the same requirement but materially different scenario/expected outcome must not be incorrectly collapsed.

The governing principle is:

> Same requirement + same scenario + same expected outcome should not produce equivalent testcases merely because wording differs.
