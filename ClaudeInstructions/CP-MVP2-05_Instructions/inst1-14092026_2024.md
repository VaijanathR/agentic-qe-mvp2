# 2. OBJECTIVE

Create the canonical specification:

`docs/CP-MVP2-05-SPECIFICATION-v1.0.md`

Title:

**CP-MVP2-05 — Playwright E2E Generation**

The specification must define how the Agentic QE system consumes:

**Approved SRS → governed RAG evidence → accepted CP-MVP2-03 testcase → governed CP-MVP2-04 test data**

and produces:

**governed, traceable Playwright E2E test specifications / executable-test generation inputs**

for the Demo Web Shop.

The objective is NOT merely to generate Playwright code.

The objective is to establish a governed transformation from an already accepted testcase and its governed test data into a browser automation artifact without reinterpreting or changing business requirements.

---

# 3. AUTHORITATIVE ARCHITECTURE

The specification should establish this conceptual flow:

APPROVED SRS
→ MVP2 KNOWLEDGE BASE
→ GOVERNED RAG
→ ACCEPTED CP-MVP2-03 TESTCASE
→ ACCEPTED / GOVERNED CP-MVP2-04 TEST DATA
→ PLAYWRIGHT TEST DESIGN
→ DETERMINISTIC VALIDATION
→ TRACEABILITY / GOVERNANCE
→ CP-MVP2-05 RESULT

The core architectural principle remains:

**RAG supplies evidence.**
**CP-MVP2-03 supplies the governed testcase.**
**CP-MVP2-04 supplies governed test data.**
**LLM may reason/generate Playwright artifacts.**
**Deterministic code decides structural and governance compliance.**

The LLM must NOT become the final authority for requirements, testcase validity, test-data validity, or governance.

---

# 4. DEFINE THE CP-MVP2-05 INPUT CONTRACT

Explicitly define the required inputs.

At minimum consider:

1. Accepted CP-MVP2-03 `GovernedTestcase`
2. Its valid requirement IDs
3. Governed requirement context / attribution
4. Accepted CP-MVP2-04 `TestDataSet`
5. Test-data field values and dependencies
6. Source attribution
7. Scenario type
8. Preconditions
9. Test steps
10. Expected results

CP-MVP2-05 must consume governed upstream artifacts.

It must NOT independently reinterpret requirements or silently repair an upstream testcase/data defect.

---

# 5. DEFINE THE PLAYWRIGHT ARTIFACT CONTRACT

Design a structured schema for the CP-MVP2-05 output.

Do not assume that raw source code alone is sufficient.

Consider a two-level or otherwise appropriately structured model containing, as justified:

* automation/test ID
* source testcase ID
* requirement IDs
* source test-data-set ID
* journey ID
* scenario type
* browser/environment intent
* preconditions
* navigation/actions
* locators
* input mappings
* assertions
* expected results
* synchronization strategy
* evidence requirements
* failure handling metadata
* source attribution
* generation metadata
* validation status
* governance status

The final schema must be governed and deterministic where appropriate.

Do not add fields merely for theoretical completeness.

---

# 6. LOCATOR GOVERNANCE

This is a critical part of CP-MVP2-05.

Define how locator strategies should be selected and governed.

The specification should consider a deterministic locator priority strategy based on evidence available from the application, for example:

* stable semantic/test IDs where available
* accessible roles/names
* stable attributes
* labels
* other deterministic selectors

Avoid fragile selectors such as arbitrary DOM hierarchy or generated CSS/XPath unless justified.

Do not invent locators that have not been evidenced by the application.

If locator evidence is unavailable, define a governed:

`UNSUPPORTED / NEEDS CLARIFICATION`

or equivalent outcome rather than allowing the LLM to fabricate an apparently valid locator.

The specification must clearly distinguish:

**locator generation**
from
**locator validation**

---

# 7. APPLICATION / DOM EVIDENCE

Define how CP-MVP2-05 obtains application evidence required to construct reliable Playwright actions.

Explicitly decide what is:

* available from the existing knowledge base
* available from application discovery
* obtained through controlled browser inspection
* unavailable until CP-MVP2-06

Do not silently assume browser inspection capabilities that belong to CP-MVP2-06.

CP-MVP2-05 should define the boundary between:

**test generation**

and

**real browser execution**.

---

# 8. PLAYWRIGHT GENERATION BOUNDARY

CP-MVP2-05 may generate Playwright artifacts.

It must NOT execute the generated tests against the real browser unless that capability is explicitly and deliberately assigned to CP-MVP2-06.

CP-MVP2-06 remains:

**Real Browser Execution**

Define the downstream contract clearly.

---

# 9. TEST DATA MAPPING

Every generated input must be traceable to the accepted CP-MVP2-04 dataset.

Examples:

`email`
→ CP-04 dataset field `email`

`password`
→ CP-04 dataset field `password`

etc.

The generator must not silently replace governed values with invented values.

If a required UI field has no corresponding governed data:

`UNSUPPORTED / NEEDS CLARIFICATION`

must be available.

---

# 10. ASSERTION GOVERNANCE

Define how expected results from CP-MVP2-03 become Playwright assertions.

Assertions must be grounded in:

* testcase expected result
* Approved SRS evidence
* governed application evidence where required

Do not create assertions merely because an LLM thinks they would be useful.

Distinguish:

* required business assertions
* useful technical assertions
* optional diagnostics

so optional diagnostics cannot falsely inflate requirement coverage.

---

# 11. TRACEABILITY

Require deterministic traceability:

Playwright artifact
→ CP-MVP2-03 testcase
→ requirement ID
→ Approved SRS
→ RAG evidence

and:

Playwright input
→ CP-MVP2-04 dataset
→ test-data field

No orphan automation artifacts.

No unknown requirement IDs.

No unknown testcase IDs.

No unknown dataset IDs.

---

* ACCEPTED

# 13. FAILURE / AMBIGUITY HANDLING

Explicitly cover:

* missing locator evidence
* ambiguous UI element
* missing test-data field
* testcase/data mismatch
* unsupported browser interaction
* requirement ambiguity
* conflicting evidence
* unstable selector evidence
* unsupported control/widget
* dependency unavailable
* application evidence unavailable

The system must report the problem rather than inventing a solution that changes the business requirement.

---

# 14. SELF-HEALING BOUNDARY

Do NOT implement self-healing in CP-MVP2-05.

However, define whether CP-MVP2-05 records sufficient evidence for future RCA/replanning/self-healing in CP-MVP2-07.

The specification must not allow "self-healing" to silently alter:

* requirements
* testcase intent
* test data
* expected results

No real PII, payment credentials, secrets, or production credentials.

Define appropriate configuration/environment-variable handling where required, without prematurely implementing CI/CD or production infrastructure.

* schema validity
* testcase traceability

* assertion presence
* governance status
* unsupported conditions
* duplicate detection where applicable
* coverage calculation

# 21. ACCEPTANCE CRITERIA

Create measurable acceptance criteria covering:

### Functional

Generated Playwright artifact correctly represents the accepted testcase.

### Traceability

Every artifact maps to valid requirement/testcase/test-data IDs.

### Governance

No requirement/testcase/test-data reinterpretation.

### Locator integrity

Locators are evidence-based or explicitly quarantined/unsupported.

### Assertion integrity

Assertions derive from governed expected results.

### Data integrity

Generated inputs come from CP-MVP2-04 governed data.

### Deterministic validation

Invalid artifacts cannot be accepted.

### Coverage

Coverage is calculated deterministically and cannot be inflated.

### Regression

Existing CP-MVP2-01 through CP-MVP2-04 behavior remains unchanged.
